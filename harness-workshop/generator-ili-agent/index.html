Часть 3 · Работа по плану · Урок 6

Генератор или агент: что выгоднее генерировать по правилам

Часть кода пишется по правилам: DTO, миграции, клиенты API, типы. Агент сделает это каждый раз немного по-разному и за токены. Генератор сделает одинаково, бесплатно и мгновенно. Разберём, где граница.

~45 минут 3 интерактива 11 вопросов Примеры: JS · TS · PHP · Python

После урока вы сможете

  • объяснить, что такое детерминированный генератор и почему это важно;
  • объяснить формулу «спецификация плюс шаблон равно код» и собрать по ней простой генератор;
  • решать, что отдать генератору, что агенту, а что делать вместе;
  • защитить сгенерированный код от ручных правок и проверить генерацию в CI.
1 Аналогия

Формочка для печенья и лепка руками

Представьте

Сто одинаковых печений проще выдавить формочкой, чем лепить руками. Руками лепят торт на заказ: он один, и он особенный.

Формочка (генератор)

Руками (агент)

Партия 1: слева все одинаковые, справа каждая своя.
Формочка= шаблон генератора
Тесто= спецификация: JSON, OpenAPI, схема
Печенье= сгенерированный код
Кондитер с тортом на заказ= агент на нестандартной логике
«Все печенья одинаковые?»= проверка в CI: генерация не даёт диффа

Главная мысль: то, что делается по правилам, делайте правилами. Агента оставьте там, где нужны понимание и решения.

2 Объяснение

От простого к сложному

Уровень 1 · Суть

Шаблон плюс данные равно код

Детерминированный (предсказуемый) значит: тот же вход даёт тот же выход, байт в байт. Модель из урока 1 так не умеет: выбор токенов случайный. Обычная функция умеет.

Генератор кода — это функция. На вход — описание (спецификация). Внутри — шаблон. На выход — текст программы.

const entity = { name: "Order", fields: [{ name: "id", type: "number" }, { name: "email", type: "string" }] };

const ts = `export interface ${entity.name} {
${entity.fields.map(f => `  ${f.name}: ${f.type};`).join("\n")}
}`;
// export interface Order {
//   id: number;
//   email: string;
// }
<?php
$entity = ['name' => 'Order', 'fields' => [['name' => 'id', 'type' => 'number'], ['name' => 'email', 'type' => 'string']]];

$lines = array_map(fn ($f) => "  {$f['name']}: {$f['type']};", $entity['fields']);
$ts = "export interface {$entity['name']} {\n" . implode("\n", $lines) . "\n}";
// export interface Order {
//   id: number;
//   email: string;
// }
entity = {"name": "Order", "fields": [{"name": "id", "type": "number"}, {"name": "email", "type": "string"}]}

lines = "\n".join(f"  {f['name']}: {f['type']};" for f in entity["fields"])
ts = f"export interface {entity['name']} {{\n{lines}\n}}"
# export interface Order {
#   id: number;
#   email: string;
# }
Что важноЗапустите эту функцию сто раз — получите сто одинаковых файлов. Попросите агента сто раз — получите сто немного разных.
Уровень 2 · Детали

Где живут генераторы и где граница с агентом

Вы почти наверняка уже пользовались генераторами:

  • OpenAPI (описание API) превращается в клиентов, DTO и заготовки контроллеров;
  • JSON Schema превращается в типы TypeScript, Python, PHP;
  • описание сущности превращается в Entity, миграцию, репозиторий (в Symfony это make:entity и doctrine:migrations:diff);
  • protobuf превращается в клиентов и серверы gRPC.

Генератору отдавайте: CRUD, DTO, контракты API, маппинги, типы, миграции. Всё, что повторяется и следует правилу.

Агенту оставляйте: нестандартную бизнес-логику, рефакторинг, разбор багов, склейку систем. Всё, где нужно понять смысл.

Гибрид работает лучше всего. Агент пишет или правит спецификацию (это короткий понятный файл). Генератор делает из неё код. Агент дописывает бизнес-логику в оставленные для неё места.

Мини-генератор SQL на четырёх языках — шаблонные строки

Один и тот же генератор: JSON с описанием сущности на входе, CREATE TABLE на выходе.

import { readFileSync, writeFileSync } from "node:fs";

const SQL = { int: "INTEGER", string: "VARCHAR", text: "TEXT", bool: "BOOLEAN", decimal: "NUMERIC(12, 2)", datetime: "TIMESTAMP" };
const snake = s => s.replace(/[A-Z]/g, c => "_" + c.toLowerCase());

function column(f) {
  let type = SQL[f.type];
  if (f.type === "string") type += `(${f.length ?? 255})`;
  const parts = [snake(f.name), type];
  if (f.primary) parts.push("PRIMARY KEY");
  else if (!f.nullable) parts.push("NOT NULL");
  if (f.unique) parts.push("UNIQUE");
  return "  " + parts.join(" ");
}

const e = JSON.parse(readFileSync("entities/order.json", "utf8"));
const sql = `-- GENERATED from entities/order.json. Do not edit.\nCREATE TABLE ${e.table} (\n${e.fields.map(column).join(",\n")}\n);\n`;
writeFileSync(`migrations/${e.table}.sql`, sql);
import { readFileSync, writeFileSync } from "node:fs";

type FieldType = "int" | "string" | "text" | "bool" | "decimal" | "datetime";
interface Field { name: string; type: FieldType; length?: number; nullable?: boolean; unique?: boolean; primary?: boolean }
interface Entity { name: string; table: string; fields: Field[] }

const SQL: Record<FieldType, string> = { int: "INTEGER", string: "VARCHAR", text: "TEXT", bool: "BOOLEAN", decimal: "NUMERIC(12, 2)", datetime: "TIMESTAMP" };
const snake = (s: string): string => s.replace(/[A-Z]/g, c => "_" + c.toLowerCase());

function column(f: Field): string {
  const type = f.type === "string" ? `VARCHAR(${f.length ?? 255})` : SQL[f.type];
  const parts = [snake(f.name), type];
  if (f.primary) parts.push("PRIMARY KEY");
  else if (!f.nullable) parts.push("NOT NULL");
  if (f.unique) parts.push("UNIQUE");
  return "  " + parts.join(" ");
}

const e: Entity = JSON.parse(readFileSync("entities/order.json", "utf8"));
writeFileSync(`migrations/${e.table}.sql`, `CREATE TABLE ${e.table} (\n${e.fields.map(column).join(",\n")}\n);\n`);
<?php
// bin/generate-sql.php entities/order.json
$sqlTypes = ['int' => 'INTEGER', 'text' => 'TEXT', 'bool' => 'BOOLEAN', 'decimal' => 'NUMERIC(12, 2)', 'datetime' => 'TIMESTAMP'];
$snake = fn (string $s): string => strtolower(preg_replace('/[A-Z]/', '_$0', $s));

$e = json_decode(file_get_contents($argv[1]), true, flags: JSON_THROW_ON_ERROR);
$columns = [];
foreach ($e['fields'] as $f) {
    $type = $f['type'] === 'string' ? sprintf('VARCHAR(%d)', $f['length'] ?? 255) : $sqlTypes[$f['type']];
    $parts = [$snake($f['name']), $type];
    if ($f['primary'] ?? false) {
        $parts[] = 'PRIMARY KEY';
    } elseif (!($f['nullable'] ?? false)) {
        $parts[] = 'NOT NULL';
    }
    if ($f['unique'] ?? false) {
        $parts[] = 'UNIQUE';
    }
    $columns[] = '  ' . implode(' ', $parts);
}
file_put_contents("migrations/{$e['table']}.sql", "CREATE TABLE {$e['table']} (\n" . implode(",\n", $columns) . "\n);\n");
import json
import re
import sys
from pathlib import Path

SQL = {"int": "INTEGER", "text": "TEXT", "bool": "BOOLEAN", "decimal": "NUMERIC(12, 2)", "datetime": "TIMESTAMP"}

def snake(s: str) -> str:
    return re.sub(r"[A-Z]", lambda m: "_" + m.group().lower(), s)

def column(f: dict) -> str:
    t = f"VARCHAR({f.get('length', 255)})" if f["type"] == "string" else SQL[f["type"]]
    parts = [snake(f["name"]), t]
    if f.get("primary"):
        parts.append("PRIMARY KEY")
    elif not f.get("nullable"):
        parts.append("NOT NULL")
    if f.get("unique"):
        parts.append("UNIQUE")
    return "  " + " ".join(parts)

e = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
body = ",\n".join(column(f) for f in e["fields"])
Path(f"migrations/{e['table']}.sql").write_text(f"CREATE TABLE {e['table']} (\n{body}\n);\n", encoding="utf-8")
Готовый генератор по OpenAPI — пример команды

Писать свой генератор нужно не всегда. Для OpenAPI есть готовый openapi-generator с шаблонами под десятки языков. Ниже пример: фрагмент спецификации и команда генерации клиента.

Уровень 3 · Усложнение

Защита сгенерированного кода и экономика

Сгенерированный код не правят руками. Следующая генерация перезапишет правку, и она тихо пропадёт. Правят спецификацию или шаблон. Как это закрепить:

  • в начале файла метка GENERATED и откуда он получен;
  • сгенерированные файлы лежат в отдельной папке (например, generated/);
  • в правилах агента: «файлы с меткой GENERATED не правь, правь спецификацию и запусти генератор»;
  • хук (урок 4) запрещает агенту запись в такие файлы;
  • CI запускает генерацию и проверяет, что дифф пустой: make generate && git diff --exit-code.

Где детерминированность ломается. Дата генерации в шапке файла, случайные id, порядок ключей словаря, разные версии генератора у разных разработчиков. Каждое из этого даёт дифф без изменений спецификации, и CI-проверка становится бесполезной. Версию генератора фиксируйте, дату не пишите, поля сортируйте стабильно.

Экономика40 DTO по спецификации партнёра. Агент: десятки тысяч токенов, полчаса ревью, и при обновлении спецификации всё заново, с новыми мелкими отличиями. Генератор: день на настройку один раз, потом секунды и ноль ревью шаблонного кода. Чем чаще повторяется задача, тем выгоднее генератор.
Проверка генерации в CI — Makefile и GitHub Actions 
# Makefile
generate:
	node bin/generate-sql.mjs entities/*.json
	npx @openapitools/openapi-generator-cli generate -i openapi.yaml -g typescript-fetch -o src/api

check-generated: generate
	git diff --exit-code -- migrations/ src/api/ || (echo "Сгенерированный код устарел: запустите make generate" && exit 1)
# .github/workflows/ci.yml (фрагмент)
- name: Сгенерированный код совпадает со спецификацией
  run: make check-generated

        4 Тесты
        
    Проверьте себя
    
        
    Код писать не нужно. Где верный ответ один, он засчитывается по клику. Где написано «Отметьте все верные ответы», выберите все подходящие и нажмите «Проверить»: зачёт только при точном совпадении. Ответы сохраняются в браузере.
    
      
    

      
    
        
    Вопросы по уроку
    
        
    
          
    Что значит «детерминированный генератор»?
    
          
    
            
            
            
          
    
          
    Поэтому результат можно проверять в CI сравнением: если дифф не пустой, значит спецификация и код разошлись.
    
        
    
        
    
          
    Какую задачу выгоднее отдать генератору, а не агенту?
    
          
    
            
            
            
          
    
          
    Повторяемо, по правилу, обновляется регулярно. Остальные две задачи требуют понимания: это работа агента.
    
        
    
        
    
          
    Агент поправил руками файл с меткой GENERATED. Что произойдёт?
    
          
    
            
            
            
          
    
          
    Поэтому в правилах агента пишут «не правь GENERATED», а хук может запретить такую запись.
    
        
    
        
    
          
    Почему не стоит писать дату генерации в шапку файла?
    
          
    
            
            
            
          
    
          
    Это ловит проверка детерминированности: прогнать генератор несколько раз и сравнить результаты. То же со случайными id и нестабильным порядком полей.
    
        
    
        
    
          
    Что выгодно отдать генератору?
    
          
    
            
            
            
            
          
    
          
    Генератору — всё, что повторяется и следует правилу: типы, клиенты, миграции, DTO. Разбор редкого бага требует понимания и гипотез — это работа агента.
    
        
    
        
    
          
    Что ломает детерминированность генератора?
    
          
    
            
            
            
            
          
    
          
    Каждое из первых трёх даёт дифф без изменений спецификации, и проверка в CI становится бесполезной. Метка GENERATED одинакова в каждом прогоне: она не мешает, а защищает файл от ручных правок.
    
        
    
        
    
          
    Как защитить сгенерированный код от ручных правок агента?
    
          
    
            
            
            
            
          
    
          
    Метка и правило объясняют агенту, хук не даёт записать, CI ловит то, что всё же проскочило. Просьба в чате пропадёт вместе с сессией и ничего не гарантирует.
    
        
    
        
    
          
    Генератор переводит типы спецификации в TypeScript. Какие правила разумны?
    
          
    
            
            
            
            
          
    
          
    Деньги во float теряют копейки, поэтому decimal передают строкой. Nullable должен быть виден в типе. Целые числа в JS точны до 2⁵³ — строка тут не нужна. Часовой пояс машины делает вывод разным у разных людей: это ломает детерминированность.
    
        
    
        
    
          
    Генератор делает CREATE TABLE по сущности Order. Что верно?
    
          
    
            
            
            
          
    
          
    Правила простые и всегда одинаковые — поэтому их и отдают генератору. Случайный порядок дал бы новый дифф на каждом прогоне.
    
        
    
        
    
          
    Как лучше всего работать в паре генератор и агент?
    
          
    
            
            
            
          
    
          
    Пара работает так: спецификацию агенту править легко, шаблонный код генератор делает без токенов, а нестандартную логику пишет агент — там нужно понимание.
    
        
    
        
    
          
    CI выполнил make generate && git diff --exit-code и упал. Что это значит?
    
          
    
            
            
            
          
    
          
    Проверка сравнивает свежую генерацию с тем, что лежит в репозитории. Дифф значит расхождение. Чинят так: правку переносят в спецификацию или шаблон и генерируют заново.
