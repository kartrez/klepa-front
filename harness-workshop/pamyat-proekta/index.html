Часть 2 · Агент в вашем проекте · Урок 3

Память проекта: что агенту знать заранее и как это хранить

Модель ничего не помнит между сессиями. Всё, что агент должен знать о проекте, надо где-то хранить и вовремя ему подавать. Разберём, что хранить, как раскладывать и как доставать без лишних токенов.

~50 минут 4 интерактива 12 вопросов Примеры: JS · TS · PHP · Python

После урока вы сможете

  • объяснить, зачем агенту внешняя память и чем она отличается от окна контекста;
  • разложить знания проекта на заметки: правила, решения, справку, грабли;
  • выбрать способ выдачи знаний: всё сразу, оглавление или поиск;
  • написать простой поиск по заметкам с бюджетом токенов;
  • не дать устаревшей заметке сломать работу агента.
1 Аналогия

Библиотекарь с каталогом

Представьте

Новому сотруднику не читают вслух всю вики компании. Ему дают оглавление и говорят: «Нужно что-то — найди по каталогу». На столе лежат только книги для текущей задачи.

Как библиотекарь находит ответ

схема
Вопрос«Как выкатить бэкенд?»
→
Каталогоглавление: 40 заметок, по строке на каждую
→
Полкаберём 2 подходящие заметки
→
Столтолько они попадают в контекст
На столе пусто.
Блокнот и вики новичка= заметки памяти агента
Оглавление вики= индекс (одна строка на заметку)
Библиотекарь= поиск нужного по задаче
Рабочий стол= окно контекста
Устаревшая страница вики= заметка, которая разошлась с кодом

Главная мысль: хорошая память — это не «запомнить всё». Это быстро найти нужное и не тащить лишнее. Каждая лишняя заметка на столе стоит денег и мешает модели заметить главное.

2 Объяснение

От простого к сложному

Уровень 1 · Суть

Внешняя память — это папка с текстом и правило, как её читать

Из урока 1 вы знаете: модель не хранит состояние. Закрыли сессию — всё забыто. Окно контекста ограничено. Значит, знания о проекте надо держать снаружи, в обычных файлах. Это и называют Second Brain (второй мозг).

Схема простая. Перед задачей harness читает оглавление, выбирает подходящие заметки и кладёт их в контекст. После задачи агент дописывает новое знание.

context.push(...picked.map(name => read(`memory/${name}.md`)));

Уровень 2 · Детали

Что хранить и как раскладывать

Пять видов знаний, которые окупаются почти в любом проекте:

  • Правила проекта. «Деньги храним в копейках, целым числом». «Миграции только через Doctrine».
  • Архитектурные решения. Формат ADR: контекст, решение, последствия. Объясняет «почему так», чтобы агент не «улучшил» обратно.
  • Справка. Как запустить проект, тесты, деплой. Команды, которые агент выполнит сам.
  • Продуктовый контекст. Кто пользователи, что для бизнеса важно, какие слова нельзя писать клиентам.
  • Грабли. Инциденты и их причины: «перезапуск воркера руками обрывает очередь».

Как раскладывать. Одна мысль — один маленький файл. В начале файла — frontmatter: имя, однострочное описание, тип. Отдельный файл-оглавление собирает по строке на каждую заметку. Заметки ссылаются друг на друга через [[имя]].

---
name: money-in-kopecks
description: Деньги храним целым числом в копейках, никогда не float
type: rule
updated: 2026-09-14
---
Все суммы в БД и коде — integer в копейках (1 BYN = 100).
Float теряет точность: 0.1 + 0.2 != 0.3.
Связано: [[adr-003-money-type]], [[incident-refund-rounding]]

Три способа выдачи знаний агенту:

  • Всё сразу. Склеить все заметки в системный промпт. Просто, но дорого. При росте базы важное тонет в шуме.
  • Оглавление и подгрузка. Агент видит только индекс и сам открывает нужные файлы. Дёшево, точно, но требует хороших описаний.
  • Поиск. Программа находит заметки по тексту задачи и подкладывает их. Работает на больших базах. Может промахнуться.

Пример ADR — контекст, решение, последствия 
# ADR-003. Тип для денежных сумм

Статус: принято, 2026-03-02

## Контекст
Суммы хранились во float. При возвратах накопились расхождения в 1 копейку.

## Решение
Храним суммы целым числом в копейках (BIGINT). В коде — value object Money.

## Последствия
+ Нет ошибок округления.
- При выводе нужно делить на 100. Все старые колонки переводим миграцией.
- Внешние API, которые отдают float, переводим в копейки на входе.
AGENTS.md, который отсылает к памяти — точка входа для агента

Файл правил (урок 2) остаётся коротким. Он не пересказывает всё, а говорит, где искать.

# Правила для агента

- Перед задачей прочитай memory/INDEX.md и открой заметки по теме.
- Заметка — подсказка, а не правда. Перед действием сверь её с кодом.
- Если заметка разошлась с кодом — прав код. Исправь заметку и обнови дату.
- Новое знание (решение, грабли) — отдельной заметкой и строкой в INDEX.md.
- Как запускать тесты и деплой — docs/howto/*.md, не выдумывай команды.
Уровень 3 · Усложнение

Поиск по смыслу, устаревание и иерархия правды

Поиск по словам находит заметки, где есть слова из запроса. Простой подсчёт совпадений работает плохо: частые слова вроде «код» есть везде. Алгоритм BM25 даёт больший вес редким словам и не любит слишком длинные документы.

Поиск по смыслу решает проблему синонимов. «Деплой» и «выкатка» — разные слова, но смысл один. Текст превращают в эмбеддинг: координаты смысла. Представьте карту, где похожие по смыслу фразы лежат рядом. Поиск — это «найди точки рядом с вопросом». Схему «найти, подложить в контекст, ответить» называют RAG.

Устаревание — главная беда любой базы знаний. Код меняют каждый день, а заметки — редко. Правила гигиены:

  • в заметке есть дата обновления;
  • перед действием агент сверяет заметку с кодом;
  • нашёл расхождение — исправил заметку сразу, а не завёл вторую рядом;
  • противоречивые заметки — это баг, его чинят.
Иерархия источников правдыКогда источники спорят, побеждает старший: прямое указание человека в задаче, потом код и тесты, потом спецификации (урок 5), потом документация, и только потом заметки памяти. Память лишь подсказывает, где смотреть.
BM25 и косинусная близость без страха — для любопытных

BM25 для каждого слова запроса считает два множителя и складывает результат по всем словам:

  • IDF (редкость слова): чем в меньшем числе заметок встречается слово, тем оно ценнее. «Doctrine» ценнее, чем «проект».
  • TF с насыщением: второе упоминание слова в заметке добавляет меньше, чем первое, десятое — почти ничего. Длинные заметки слегка штрафуются.
score(док, запрос) = Σ IDF(слово) · tf·(k+1) / (tf + k·(1 − b + b·длина/средняя_длина))
обычно k ≈ 1.2, b ≈ 0.75

близость(a, b) = (a · b) / (|a| · |b|)   ← косинус угла между векторами смысла, от −1 до 1

Эмбеддинги считает отдельная модель. Векторы хранят в базе с поиском ближайших соседей (например, расширение pgvector для Postgres). На старте проекта часто хватает обычного поиска по словам и хорошего оглавления.

Простой поиск по заметкам в коде — JS, TS, PHP, Python

Подсчёт совпавших слов без стоп-слов. Не BM25, но для базы из сотни заметок уже полезно.

import { readdirSync, readFileSync } from "node:fs";

const STOP = new Set(["и", "в", "на", "как", "что", "по", "с", "для", "не"]);
const words = s => s.toLowerCase().match(/[a-zа-яё0-9]+/g)?.filter(w => !STOP.has(w)) ?? [];

function search(dir, query, limit = 3) {
  const q = new Set(words(query));
  return readdirSync(dir)
    .filter(f => f.endsWith(".md"))
    .map(f => {
      const text = readFileSync(`${dir}/${f}`, "utf8");
      const score = new Set(words(text).filter(w => q.has(w))).size;
      return { file: f, score };
    })
    .filter(r => r.score > 0)
    .sort((a, b) => b.score - a.score)
    .slice(0, limit);
}

interface Hit { file: string; score: number }

const STOP = new Set(["и", "в", "на", "как", "что", "по", "с", "для", "не"]);
const words = (s: string): string[] =>
  (s.toLowerCase().match(/[a-zа-яё0-9]+/g) ?? []).filter(w => !STOP.has(w));

export function search(dir: string, query: string, limit = 3): Hit[] {
  const q = new Set(words(query));
  return readdirSync(dir)
    .filter(f => f.endsWith(".md"))
    .map((file): Hit => {
      const text = readFileSync(`${dir}/${file}`, "utf8");
      return { file, score: new Set(words(text).filter(w => q.has(w))).size };
    })
    .filter(h => h.score > 0)
    .sort((a, b) => b.score - a.score)
    .slice(0, limit);
}
<?php
const STOP = ['и', 'в', 'на', 'как', 'что', 'по', 'с', 'для', 'не'];

function words(string $s): array
{
    preg_match_all('/[a-zа-яё0-9]+/u', mb_strtolower($s), $m);
    return array_values(array_diff($m[0], STOP));
}

function search(string $dir, string $query, int $limit = 3): array
{
    $q = array_unique(words($query));
    $hits = [];
    foreach (glob($dir . '/*.md') as $file) {
        $score = count(array_intersect($q, array_unique(words(file_get_contents($file)))));
        if ($score > 0) {
            $hits[] = ['file' => basename($file), 'score' => $score];
        }
    }
    usort($hits, fn ($a, $b) => $b['score'] <=> $a['score']);
    return array_slice($hits, 0, $limit);
}

import re
from pathlib import Path

STOP = {"и", "в", "на", "как", "что", "по", "с", "для", "не"}

def words(s: str) -> list[str]:
    return [w for w in re.findall(r"[a-zа-яё0-9]+", s.lower()) if w not in STOP]

def search(folder: str, query: str, limit: int = 3) -> list[tuple[str, int]]:
    q = set(words(query))
    hits = []
    for path in Path(folder).glob("*.md"):
        score = len(q & set(words(path.read_text(encoding="utf-8"))))
        if score:
            hits.append((path.name, score))
    return sorted(hits, key=lambda h: -h[1])[:limit]

      Поэтому поиск по эмбеддингам находит «выкатку» по запросу «деплой»: слова разные, смысл рядом.
      
        
      
        
      
          
      Что из этого стоит положить в память проекта?
      
          
      
            
            
            
            
          
      
          
      Правило, грабли и решение ADR — короткие знания, которых нет в коде, а ошибиться без них легко. Выгрузка данных — не знание о проекте: она огромная, быстро устаревает и может содержать личные данные клиентов.
      
        
      
        
      
          
      Как устроена хорошая заметка в памяти?
      
          
      
            
            
            
            
          
      
          
      Маленькую заметку дёшево подложить в контекст и легко обновить. Описание из frontmatter попадает в оглавление — по нему агент решает, открывать ли файл. Ссылки ведут к соседним темам. Один большой файл — это «всё сразу» со всеми его минусами.
      
        
      
        
      
          
      Агент видит только оглавление INDEX.md. От чего зависит, откроет ли он нужную заметку?
      
          
      
            
            
            
          
      
          
      Модель выбирает по тексту, который видит. Строка «deploy-backend — выкатка бэкенда: только make up» сразу говорит, когда она нужна. Строка «заметки про сервер» не говорит ничего.
      
        
      
        
      
          
      Поиск отсортировал заметки по очкам: A — 40 токенов, B — 25, C — 10. Бюджет — 50 токенов. Что он возьмёт по правилу из урока?
      
          
      
            
            
            
          
      
          
      Идём по списку и берём, что влезает. После A осталось 10 токенов. B на 25 не влезает — её пропускаем, но не останавливаемся. C на 10 влезает ровно. Так бюджет используется полностью.
      
        
      
        
      
          
      Источники спорят. Что верно про иерархию правды?
      
          
      
            
            
            
            
          
      
          
      Порядок такой: человек, код и тесты, спецификации, документация, память. Память — подсказка, где смотреть. Если она спорит с кодом, устарела заметка, а не код.
      
        
      
        
      
          
      Запрос «как выкатить» не нашёл заметку со словом «выкатка». Что поможет?
      
          
      
            
            
            
            
          
      
          
      Поиск по словам сравнивает буквы: «выкатить» и «выкатка» для него разные. Стемминг сводит их к общему началу, эмбеддинги ставят рядом по смыслу. Бюджет и повтор не помогут: заметка просто не попала в найденное.
      
        
      
        
      
          
      Почему простой подсчёт совпавших слов ищет плохо, а BM25 — лучше?
      
          
      
            
            
            
          
      
          
      Слово «Doctrine» говорит о заметке больше, чем слово «проект». BM25 это учитывает и не даёт длинным заметкам выигрывать числом слов. Но он всё ещё сравнивает слова — синонимы находит поиск по смыслу.
      
        
      
        
      
          
      Агент пишет новый ADR. Что harness стоит проверить перед сохранением?
      
          
      
            
            
            
            
          
      
          
      Формат ADR простой, и его легко проверить кодом до записи. Пустое «Решение» хуже, чем никакого: агент потом примет его за принятое решение. Примеры кода в ADR не обязательны — важно, почему так решили.
      
        
      
      
      

      
      
        Задание на своём проекте — 30 минут
        
      
          
        
            
      1. Создайте в репозитории папку memory/ (или docs/agent/).
        2. 
            
      2. Напишите пять заметок с frontmatter: как запустить проект, как запустить тесты, одно правило, одно архитектурное решение в формате ADR, одни грабли из вашей практики.
        3. 
            
      3. Соберите INDEX.md: по строке на заметку, с хорошим описанием. Проверьте: по одной строке понятно, когда открывать заметку?
        4. 
            
      4. Добавьте в файл правил агента три строки: «прочитай INDEX.md», «сверяй заметку с кодом», «нашёл расхождение — исправь заметку».
        5. 
            
      5. Дайте агенту задачу, где пригодится одна из заметок. Посмотрите, открыл ли он её.
