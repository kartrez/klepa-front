Часть 5 · Большие проекты · Урок 9

Агент в старом проекте: как подготовить legacy и внедрять постепенно

AI-First — это не «подключить чат к IDE». Это сделать проект понятным и проверяемым, чтобы агент мог в нём работать. Разберём паттерны для старых проектов и порядок внедрения.

~50 минут 4 интерактива 3D-фильм и 11 вопросов Примеры: JS · PHP · Python · Markdown

После урока вы сможете

  • оценить, насколько ваш проект готов к работе с агентами;
  • назвать семь паттернов, которые делают legacy понятным для агента;
  • составить план внедрения: какие задачи давать агенту первыми, а какие позже;
  • заменить старый модуль по частям, не останавливая систему.
1 Аналогия

Склад переходит на роботов

Представьте

Старый склад: коробки где попало, схема только в голове кладовщика. Если запустить туда робота, он будет ездить кругами и ронять полки. Сначала размечают полки, потом ставят датчики, потом пускают робота на простой участок.

Агент работает так же хорошо, как хорошо устроена среда вокруг него. В понятном проекте с быстрыми проверками он полезен. В хаосе — опасен.

2 Объяснение

От простого к сложному

Сначала короткий фильм — 43 секунды: старый проект как город, где здания — файлы. Остановите в любой момент, перемотайте, поверните город мышью и кликните по зданиям.

Уровень 1 · Суть

Агенту нужны карта и обратная связь

Новый разработчик в команде первые недели спрашивает: где что лежит, как запустить, как проверить. У агента та же проблема, только спросить ему некого, а памяти между сессиями нет. Поэтому ответы должны лежать в проекте.

Две вещи решают почти всё:

  • Карта. Где модули, какие правила, что нельзя трогать. Это файл правил для агента и короткие README.
  • Обратная связь. Одна команда, которая за минуты говорит: «всё хорошо» или «сломано вот тут». Тесты, линтер, проверка типов.
ПримерЗадача: «почини расчёт скидки». В проекте без тестов агент поправит формулу и скажет «готово». Проверить нечем. В проекте с тестами он запустит их, увидит красный тест про скидку для оптовиков и исправит до того, как вы откроете PR.
Уровень 2 · Детали

Семь паттернов AI-First

  1. Карта проекта и правила. AGENTS.md (или CLAUDE.md) в корне: как запустить, как проверить, правила кода, запреты. Короткие README в ключевых модулях.
  2. Быстрая обратная связь. Одна команда make check или composer check: тесты, линтер, статический анализ. Чем быстрее, тем чаще агент её запускает.
  3. Характеризационные тесты. Перед правкой старого кода фиксируем, как он работает сейчас, даже если странно. Агент правит — тест показывает, что поведение не уехало.
  4. Границы модулей и контракты. Чем меньше модуль связан с остальными, тем меньше контекста нужно агенту и тем меньше он сломает.
  5. Генераторы для шаблонного. CRUD, DTO, клиенты API делает генератор, а не агент (урок 6). Быстрее, дешевле, одинаково.
  6. Спецификации для изменений. Новая функциональность начинается со спеки, а не с «сделай фичу» (урок 5).
  7. Постепенное внедрение. Сначала безопасные задачи, потом средние, потом сложные. На каждом шаге — метрики.
Пример AGENTS.md для legacy-проекта — шаблон

Коротко и по делу. Агент читает этот файл в начале каждой сессии, поэтому каждая строка стоит токенов.

# Магазин — правила для агента

## Запуск и проверка
- Поднять: `docker compose up -d`
- Проверить всё: `make check` (тесты + PHPStan + php-cs-fixer, ~3 мин)
- Один тест: `vendor/bin/phpunit --filter ИмяТеста`

## Карта
- `src/Order/` — заказы и расчёт цены. Владелец: команда Checkout.
- `src/Billing/` — платежи. Любая правка — только с тестом.
- `legacy/` — старый код. Не рефакторить без характеризационных тестов.

## Правила
- Деньги — только в копейках (int), никаких float.
- Миграции БД не писать без отдельной задачи.
- Не трогать `config/secrets/` и `.env`.

## Готово, если
- `make check` зелёный;
- на новое поведение есть тест;
- в описании PR — что и зачем изменено.
Одна команда «проверь всё» — PHP, JS, Python 
{
  "scripts": {

    "stan": "phpstan analyse --no-progress",
    "cs": "php-cs-fixer fix --dry-run --diff",

  }
}

Уровень 3 · Усложнение

Как внедрять, не ломая систему и команду

Лестница задач. Сначала агент только читает и объясняет код. Потом пишет тесты и документацию. Потом чинит мелкие баги, где есть тест. Потом делает средние фичи по спеке. Сложные изменения с деньгами и миграциями — последними и с человеком на ключевых шагах.

Удушающее дерево (strangler fig). Старый модуль не переписывают целиком. Ставят перед ним фасад и по одной функции переносят в новый код. Новый код агент пишет по спеке и с тестами, старый тем временем продолжает работать.

Метрики внедрения. Сколько задач решено с агентом, время от задачи до PR, доля откатов и регрессий, стоимость на задачу. Если откатов стало больше — притормозите и усильте проверки.

Люди и процесс. За код агента отвечает человек, который открыл PR. Ревью остаётся. Команде нужно обучение: как ставить задачи, как читать сессию агента, когда остановить его.

Анти-паттерныАгенту дали доступ к проду. «Большой взрыв»: переписать всё за месяц агентами. Внедрение без тестов: агент быстро производит код, который никто не может проверить.
Характеризационный тест — PHP, Python, JS

Мы не знаем, правильно ли старый код считает доставку. Но знаем, что сейчас клиенты платят именно так. Фиксируем текущие ответы на реальных входах. Потом агент рефакторит — тест следит, чтобы ничего не уехало.

<?php
use PHPUnit\Framework\Attributes\DataProvider;
use PHPUnit\Framework\TestCase;

final class LegacyShippingCharacterizationTest extends TestCase
{
    // Значения сняты с текущего прода. Странное (бесплатно при 0 кг) — тоже фиксируем.
    public static function cases(): iterable
    {
        yield 'лёгкая посылка' => [0.5, 'MINSK', 350];
        yield 'тяжёлая посылка' => [12.0, 'MINSK', 1890];
        yield 'регион' => [2.0, 'BREST', 790];
        yield 'вес 0 — так сейчас' => [0.0, 'MINSK', 0];
    }

    #[DataProvider('cases')]
    public function testKeepsCurrentBehaviour(float $kg, string $city, int $expectedKopecks): void
    {
        self::assertSame($expectedKopecks, legacy_calc_shipping($kg, $city));
    }
}
import pytest
from legacy.shipping import calc_shipping

# Значения сняты с текущего поведения. Не «как должно быть», а «как есть».
@pytest.mark.parametrize("kg, city, expected", [
    (0.5, "MINSK", 350),
    (12.0, "MINSK", 1890),
    (2.0, "BREST", 790),
    (0.0, "MINSK", 0),   # странно, но так сейчас работает прод
])
def test_keeps_current_behaviour(kg, city, expected):
    assert calc_shipping(kg, city) == expected
import { test } from "node:test";
import assert from "node:assert/strict";
import { calcShipping } from "../legacy/shipping.js";

const cases = [
  [0.5, "MINSK", 350],
  [12.0, "MINSK", 1890],
  [2.0, "BREST", 790],
  [0.0, "MINSK", 0], // фиксируем как есть
];

for (const [kg, city, expected] of cases) {
  test(`доставка ${kg} кг в ${city}`, () => {
    assert.equal(calcShipping(kg, city), expected);
  });
}

4 Тесты

Проверьте себя

Код писать не нужно. Где верный ответ один, он засчитывается по клику. Где написано «Отметьте все верные ответы», выберите все подходящие и нажмите «Проверить»: зачёт только при точном совпадении. Ответы сохраняются в браузере.

Вопросы по уроку

Команда решила внедрять агентов в старый проект. С чего начать?

Без карты агент блуждает, без проверок — ломает незаметно. Это фундамент, на котором работают все следующие шаги.

Что такое характеризационный тест?

Мы не всегда знаем, как «правильно». Но знаем, как работает сейчас. Тест не даст агенту случайно это поменять.

Как работает паттерн strangler fig?

Замена идёт маленькими шагами. Каждый шаг можно проверить и откатить. Когда старый код больше не получает трафик, его удаляют.

Какая метрика первой покажет, что внедрение агентов вредит?

Объём кода и активность ничего не говорят о качестве. Откаты и регрессии — прямой сигнал, что проверки слабее, чем скорость.

Что агенту нужно в старом проекте в первую очередь?

Карта говорит, где что лежит и что трогать нельзя. Быстрая проверка показывает, что сломано. Доступ к проду — анти-паттерн. Огромное окно не заменяет карту: агент утонет в коде и всё равно не сможет проверить правку.

Какие задачи дать агенту в первой волне внедрения?

Первая волна — задачи с низким риском: ошибку легко заметить и откатить. Миграция платежей трогает деньги и базу — это последняя волна, со спекой и человеком на ключевых шагах.

Что повышает риск задачи для агента?

Деньги и миграции дорого ошибаются и плохо откатываются, а без тестов ошибку никто не заметит. Маленький размер и спека риск, наоборот, снижают: правку легко проверить.

Команда make check упала. Что лучше показать агенту?

Каждая строка лога занимает окно и стоит токенов. Агенту нужно ровно то, что поможет починить: какой тест упал и где. Один код выхода говорит «сломано», но не говорит что.

Какие подходы урок называет анти-паттернами?

Доступ к проду превращает ошибку агента в аварию. Большой взрыв нельзя проверить по частям. Без тестов агент быстро производит код, который никто не может проверить. Одна безопасная задача — как раз правильный старт.

Самооценка показала: тестов мало, файла правил нет. Какие шаги поднимут готовность проекта?

Готовность — это среда вокруг агента: карта, быстрая обратная связь и тесты, которые держат старое поведение. Дорогая модель в хаосе ошибается так же, только дороже.

Код написал агент, PR прошёл ревью, после релиза нашли баг. Кто за него отвечает?

Агент — инструмент. За его код отвечает тот, кто открыл PR, поэтому ревью остаётся. Команде нужно уметь читать сессию агента и вовремя его остановить.

Задание на своём проекте — 1 час
  1. Пройдите самооценку выше честно. Запишите три самые слабые области.
  2. Напишите первую версию AGENTS.md по шаблону из урока. Не больше 40 строк.
  3. Сделайте команду check. Засеките, сколько она идёт.
  4. Возьмите 10 задач из бэклога и разложите на волны по риску: деньги, миграции, размер, есть ли тесты. Первую задачу из волны 1 отдайте агенту.
