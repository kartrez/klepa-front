Много сервисов, один конвейер: контракты, порядок выкладки и фабрика агентов

Одна фича часто задевает несколько сервисов и репозиториев. Разберём, как разделить работу между агентами, не сломать соседей и как выглядит почти полностью автоматический конвейер разработки.

~55 минут 4 интерактива 11 вопросов Примеры: JS · TS · PHP · Python

После урока вы сможете

  • найти все сервисы, которые затронет изменение контракта;
  • менять API без простоя по схеме expand/contract;
  • объяснить паттерн «оркестратор и исполнители» и зачем каждому исполнителю своя копия кода;
  • понять, что такое Dark Factory и где в ней обязательно нужен человек.

2 Объяснение

От простого к сложному

Уровень 1 · Суть

Одна фича — несколько репозиториев

В микросервисах фича «промокоды» задевает заказы, оплату, сайт и письма. Это четыре репозитория, четыре набора правил и тестов. Один агент в одном контексте всё это не удержит: окно переполнится, а правки в одном сервисе сломают другой.

Поэтому работу делят. Один агент-оркестратор планирует и проверяет. Несколько агентов-исполнителей работают каждый в своём репозитории. Связывает их контракт — договорённость, какие данные один сервис отдаёт другому.

ПримерКонтракт: «orders отдаёт поле discount_minor — скидку в копейках». Исполнитель в orders его добавляет. Исполнитель в billing его читает. Им не нужно знать код друг друга, только контракт.
Уровень 2 · Детали

Карта сервисов, expand/contract и изоляция

Общий контекст. Оркестратору нужна карта: какие сервисы есть, кто чей потребитель, где лежат контракты, кто владелец. Это обычный файл в отдельном репозитории или в корне рабочего пространства.

Expand/contract (расширить, потом сузить). Сервисы выкатываются в разное время. Если переименовать поле за один шаг, потребители упадут. Поэтому так:

  1. Expand: отдаём и старое поле, и новое.
  2. Migrate: потребители по одному переходят на новое.
  3. Contract: когда старое никто не читает — удаляем его.

Оркестратор и исполнители. Оркестратор делит задачу на подзадачи, раздаёт параллельно (это называют fan-out), ждёт всех и собирает результат (fan-in). Потом запускает проверки и, если что-то упало, возвращает подзадачу исполнителю с текстом ошибки.

Изоляция. Каждому исполнителю — своя копия кода: отдельный git worktree или песочница. Иначе два агента правят один файл и затирают работу друг друга.

Контрактные тесты. Проверяют, что ответ сервиса совпадает с тем, чего ждут потребители. Они ловят несовместимость до выкладки, а не на проде.

Оркестратор с параллельными исполнителями — TS, Python, PHP

runWorker — ваш агент-исполнитель: запуск CLI агента в нужной папке или вызов API с инструментами. Здесь важна схема: план, параллельный запуск, проверка, повтор.

interface Subtask { repo: string; goal: string; contract: string }
interface Result { repo: string; ok: boolean; log: string }

async function orchestrate(feature: string): Promise<Result[]> {
  const plan: Subtask[] = await planSubtasks(feature);       // оркестратор делит задачу

  // fan-out: все исполнители работают параллельно, каждый в своём worktree
  let results = await Promise.all(plan.map(t => runWorker(t)));

  // проверка контрактов и повтор с текстом ошибки, не больше 2 раз
  for (let attempt = 0; attempt < 2; attempt++) {
    const failed = await contractTests(results);
    if (failed.length === 0) break;
    const retried = await Promise.all(
      failed.map(f => runWorker({ ...plan.find(p => p.repo === f.repo)!, goal: `Исправь: ${f.log}` })),
    );
    results = results.map(r => retried.find(x => x.repo === r.repo) ?? r);
  }
  return results;                                             // fan-in: связанные PR
}

    plan = await plan_subtasks(feature)            # [{"repo": "orders", "goal": ...}, ...]

    # fan-out: исполнители работают одновременно
    results = await asyncio.gather(*(run_worker(t) for t in plan))

    for _ in range(2):                             # не больше двух повторов
        failed = await contract_tests(results)
        if not failed:
            break
        retried = await asyncio.gather(*(
            run_worker({**t, "goal": f"Исправь: {f['log']}"})
            for f in failed for t in plan if t["repo"] == f["repo"]
        ))
        by_repo = {r["repo"]: r for r in retried}
        results = [by_repo.get(r["repo"], r) for r in results]

    return results                                 # fan-in

        $failed = $this->contracts->check($featureId);
        foreach ($failed as $f) {
            $this->bus->dispatch(new RunWorker($featureId, $f->repo, 'Исправь: ' . $f->log));
        }
    }

Уровень 3 · Усложнение

Dark Factory: конвейер без человека в цикле

Dark Factory (тёмная фабрика) — максимально автоматический конвейер. Задача, спека, реализация, проверки и готовый к поставке PR — без человека на каждом шаге.

Людям остаётся три вещи:

  • Постановка. Что делать и зачем. Хорошая задача и спека — половина результата.
  • Ворота высокого риска. Деньги, персональные данные, безопасность, необратимые миграции. Здесь решение принимает человек.
  • Разбор отказов. Каждая ошибка, которая прошла конвейер, превращается в новый тест, правило или задачу в eval-набор.

Чем меньше людей в цикле, тем сильнее должны быть автоматические проверки. Dark Factory опирается на всё, что было в курсе: правила и контекст (уроки 2, 3), спецификации (урок 5), генераторы (урок 6), контроль ошибок (урок 7) и eval-наборы (урок 8). Без них это не фабрика, а генератор незаметных поломок.

Граница автоматизацииДаже в самой автоматической фабрике агент не выкатывает на прод изменения денег и данных сам. И у него нет доступа к боевым секретам. Автоматизация готовит результат, ответственность остаётся у человека.
Как понять, что фабрика работает — метрики
  • Пропускная способность: сколько задач в сутки проходит конвейер до готового PR.
  • Сбежавшие дефекты: сколько ошибок нашли уже после выкладки. Главная метрика качества.
  • Доля переделок: сколько задач ворота вернули на доработку. Высокая доля — плохие спеки или слабые исполнители.
  • Часы людей: сколько времени уходит на ворота и разбор отказов.
  • Стоимость задачи: токены и время машин.

    4 Тесты

    Проверьте себя

    Код писать не нужно. Где верный ответ один, он засчитывается по клику. Где написано «Отметьте все верные ответы», выберите все подходящие и нажмите «Проверить»: зачёт только при точном совпадении. Ответы сохраняются в браузере.

    Вопросы по уроку

    Нужно переименовать поле в API, которым пользуются три сервиса. Какой порядок правильный?

    Сервисы выкатываются в разное время. Expand/contract гарантирует, что в каждый момент любая версия потребителя найдёт нужное поле.

    Зачем каждому агенту-исполнителю своя рабочая копия (worktree или песочница)?

    Два агента в одной папке правят одни и те же файлы и ломают сборку друг другу. Изоляция делает параллельную работу безопасной.

    Что ловят контрактные тесты?

    Каждый сервис по отдельности может быть зелёным, а вместе — не работать. Контрактные тесты проверяют именно стык.

    Что остаётся людям в Dark Factory?

    Конвейер делает рутину. Люди решают, что делать, отвечают за рискованные изменения и превращают каждую ошибку в новую проверку.

    billing и notifications читают данные из orders, а frontend — из billing. Меняется контракт orders. Кого надо проверить?

    Изменение идёт по цепочке: billing может поменять свой ответ вслед за orders, и это заденет сайт. Зелёные тесты orders проверяют только orders — стык с соседями они не видят. Обход карты должен помнить, где уже был: в графе бывают циклы.

    billing читает новое поле из orders, frontend — из billing. В каком порядке выкатывать?

    Если потребитель выйдет раньше, он будет читать поле, которого ещё нет. Одновременной выкладки не бывает: сервисы обновляются в разное время. Цикл в зависимостях — ошибка плана, его надо разорвать.

    Что делает агент-оркестратор?

    Оркестратор — прораб: планирует, раздаёт и принимает работу. Писать код во всех репозиториях сам он не должен — тогда его окно переполнится, ради чего работу и делили.

    Что должно быть в карте сервисов для оркестратора?

    Карта — короткий файл: сервисы, связи, контракты, владельцы. По ней оркестратор понимает, кого задевает задача. Исходный код читают исполнители, каждый в своём репозитории.

    Где даже в Dark Factory решение принимает человек?

    Это ворота высокого риска: ошибку там дорого или нельзя откатить. Мелкий рефакторинг внутри функции проверяют тесты, человек там не нужен.

    Какие сигналы покажут, что фабрика агентов работает плохо?

    Сбежавшие дефекты — главная метрика качества. Много переделок значит плохие спеки или слабых исполнителей. Число строк ничего не говорит о качестве, а рост скорости — хороший знак, если дефектов не прибавилось.

    Почему фичу на четыре сервиса не отдают одному агенту в одном контексте?

    Четыре репозитория — это четыре набора правил и тестов. В одном контексте агент теряет детали и не видит, где сломал соседа. Деление по контрактам даёт каждому исполнителю маленькую понятную задачу.
